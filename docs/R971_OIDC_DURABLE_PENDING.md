# R9.71 — Cross-replica confidential OIDC login pending state (source milestone)

**Product flow:** `Start on approved exact Host → CSPRNG state/nonce/PKCE verifier → PostgreSQL stores SHA256(state), S256(verifier), nonce, exact Host, three-minute expiry → HttpOnly Secure SameSite=Lax __Host- state.verifier cookie → any identically configured authorized issuer replica receives exact Host callback → compare query state with cookie in constant time → PostgreSQL atomically DELETE/RETURNING matching state hash/verifier hash/exact Host and unexpired record → reconstruct PKCE for confidential HTTPS token exchange → pinned signature+MFA+nonce/hash verification → independently restricted durable tenant browser session → same-origin authorized /dashboard`. No raw verifier, OIDC code, access token, user password or original state plaintext is stored in PostgreSQL; verifier remains HttpOnly in the browser and only its S256 appears in PostgreSQL. Database nonce is a short-lived nonsecret anti-replay challenge; session authorization never derives from this row without full real cryptographic IdP verification and active Host/tenant membership.

**Functional correction:** R9.70 singleton memory-only pending state cannot survive a replica change, so `IPAT_R971_DURABLE_PENDING=YES` selects the database-backed mode **instead of** `IPAT_R970_SINGLE_INSTANCE_OIDC=YES`. Both true or both false fail startup; live issuer setup still demands independently verified confidential IdP, nonroot isolated service, exact HTTPS issuer/Host, approved TLS edge, protected signing public key/client-secret files and the existing function-only `ipat_oidc_session_issuer_login` PostgreSQL identity. The new DB role grants this existing issuer role two narrow functions only (`begin_oidc_pending`, `consume_oidc_pending`), not SELECT/DELETE of the underlying table or tenant business privileges. Existing single-instance mode remains for isolated compatibility but **is not an HA production configuration**.

**Migration:** `deploy/db/migrations/0024_oidc_one_time_pending.sql`, additive after 0021-0023, creates FORCE-RLS table, bounded inserts serialized by exact Host, indexed expiry cleanup, atomic one-time consumption. No tenant/device records, domain lifecycle, real credential or host listener change. Back up the actual PostgreSQL cluster and demonstrate independent PITR before any real deployment migration; no schema downgrade by dropping pending rows while IdP callbacks are in progress. Only a migration-authorized DBA should apply it after reviewing existing roles and tenant IdP deployment. Keep ingress pinned to known active exact Hosts, fixed callback paths and independently reviewed TLS/SNI forwarding.

**Reproduction:** `IPAT_R971_SYNTHETIC_DOCKER=YES bash deploy/db/tests/r971_docker_repro.sh` (owner Mac lab computer with Docker, Python; no published database port, fresh synthetic database removed on exit), `cargo test --locked -p identity-core -p control-api` with pinned Rust 1.98.1, and CI `R9.71 real disposable PostgreSQL ...` runs both SQL 5 tests and a real Rust test where issuer connection A inserts and independent issuer connection B consumes the same state exactly once; wrong Host and replay fail. CI may additionally execute existing full migrations/R9.70 dashboard tests to rule out regression.

**Honest limits:** this closes the *source + disposable* HA login-pending boundary, **not production HA validation**. Full multi-pod real Keycloak with rotated signing keys, lost-session handling, CSRF hostile requests, ingress verification, real MFA, real production PostgreSQL with independently tested backup, external browser login, per-company custom domains and device operations must still be deployed and tested. Until then the old owner-private :3002 remains strictly loopback-only, the actual connected C320 is read-only, and no public production completion can be claimed.
