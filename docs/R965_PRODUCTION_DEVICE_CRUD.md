# R9.65 — Commercial-path Device metadata CRUD with correct Site retirement

**Milestone status:** production-path source + real isolated database proof; production HTTPS/IdP/PostgreSQL and physical device writes still **BLOCKED**. This is not a commercial login or public release.

## Operational workflow and boundaries

1. `Sites & POPs`: the tenant admin creates an independently registered Site before adding a device. Site has a globally unique **instance UUID within a tenant**, in addition to its human-friendly reusable stable code; every new R9.65 deployment populates site instance IDs for existing, already independently verified R9.64 Site rows. Site management and Device management remain separate modules.
2. `Devices → Add`: retain the R9.57 tenant/POP-scoped metadata Save, server-enforced compound FK and exact-idempotency. This is `SAVED`, not connected. Native ACS/USP adoption or physical OLT credentials do not appear magically after Save.
3. `Devices → View`: a currently approved tenant admin can obtain the single authorized device's full nonsecret metadata (including endpoint, never Vault reference or password) and its metadata revision. NOC remains limited to the existing secretless Site-restricted list, not full-detail endpoint access.
4. `Devices → Edit`: tenant admin supplies the exact device UUID, current revision and target **already registered** Site. Compare-and-set prevents lost updates, invalid endpoint/model/name is rejected server-side and all edits are audited with verified issuer+subject and old/new Site. Device kind/vendor/transport and `secret_ref` are NOT mutable through this ordinary edit command. If a Vault reference exists, only harmless display-name edits are permitted; credentials/site/endpoint/model transfers require a separately designed approval+adoption control. Any ongoing firmware request `AWAITING_EVIDENCE`, `APPROVED` or `EXECUTION_REQUESTED` blocks all edits. No CLI is sent by this function.
5. `Devices → Remove`: for a purely SAVED, **credentialless** record with no active firmware change, Remove means an explicitly audited **metadata archive**. It increments the revision, does not touch network hardware, removes the row from active NOC/admin lists, and retains a restricted archived listing and full admin history. Replaying the original registration request cannot silently reactivate that archived row. For devices with a Vault reference, real physical adoption or active firmware, Remove is **denied** until dedicated revocation/decommission approval and worker evidence exist; never treat inventory removal as deleting ONT services or router config.
6. **Site lifecycle correction:** archiving a candidate detaches its active `(tenant_id,pop_id)` FK and separately preserves its historical Site code, name and immutable *Site instance UUID*. After every active device has been legitimately detached, a Site may be deleted. If a Site code is later reused, the archived device retains the prior instance UUID; no historical record is silently attached to the new Site. An archived record's displayed `pop_id` means **last Site (historical)**, not current membership. Event history explicitly records `new_site=NULL` on archive. A disconnected real device is not inferred from this metadata state.

## Exact source and access control

- SQL `deploy/db/migrations/0020_managed_device_metadata_crud.sql` **requires 0019's validated FK**; it fails before any schema mutation if legacy tenant Site reconciliation is incomplete. It adds append-only `managed_device_events` under FORCE RLS; expands `ipat_managed_registry_owner` NOLOGIN grants only to needed update columns, firmware-change read guard and approved Site snapshot. Existing `ipat_managed_registry_exec` gains narrowly scoped `SECURITY DEFINER` EXECUTE only; `ipat_app_runtime` and the browser gain neither direct table nor secret access.
- Restricted DB functions: `get_managed_device_metadata` (admin nonsecret View), `edit_managed_device_metadata` (admin CAS, new Site FK, firmware/credential guard), `archive_managed_device_metadata` (admin CAS and historic Site snapshot, metadata only), and `list_managed_devices_admin` (admin keyset listing with optional archived rows and 101-row lookahead). Existing R9.57 NOC `list_managed_devices` now returns only active `SAVED` rows; existing `register_managed_device` exact replay will not return an archived entry.
- Rust `apps/control-api/src/managed_device_bff.rs` adds strict input/cursor validation and session+CSRF-gated transport-neutral calls matching the real SQL functions. Its methods are **UNMOUNTED**: until real commercially signed OIDC/MFA, trusted request Host→tenant equality, durable multi-pod sessions and deployed production PostgreSQL function-only service identities pass independent tests, enabling HTTP routes would give a false assurance of permission enforcement.
- Neither SQL nor Rust handles device credentials, sends physical SSH/Telnet/RouterOS commands, changes owner-private `DEV-01` C320 connector or edits the staged platform domain plan.

## Reproducible proof

```
IPAT_R965_SYNTHETIC_DOCKER=YES bash deploy/db/tests/r965_docker_repro.sh
```

The script requires explicit opt-in, creates a uniquely named **unpublished-port** disposable PostgreSQL 16 container, uses versioned synthetic `.invalid` seed data, applies prerequisites and the firmware migration, runs R9.64's entire independent Site and two-stage FK test suite, and then runs `deploy/db/tests/test_managed_device_metadata_crud_integration.py`. Its unconditional exit trap removes that test container. Never point this test at the actual VPS or real tenant identities. It verifies restricted SQL privileges, separate tenants, verified identity, NOC denial, CAS race, wrong-tenant Site, invalid endpoints, secret-backed and firmware-blocked edits/archives, archived replay rejection, hidden-but-admin-retrievable archived metadata, over-100-row keyset pagination and the Site-retirement regression (delete/recreate same Site code without corrupting historical identity). Pinned Rust `control-api` tests include safe input and cursor validation; source CI also runs the disposable PostgreSQL sequence in the exact existing migration order.

**Unfinished commercial release:** actual owner VPS production PostgreSQL 0018/0019/0020 migration, approval of real old-tenant Site mapping, real OIDC/MFA session and Host validation, mounted commercial HTTPS Device/Site UI/BFF, secret enrollment and safe device connection/decommission, external hostile Host/POP/tenant tests, independently restored host+database backups and public TLS are separate mandatory gates. No production migration is auto-applied by this milestone.
