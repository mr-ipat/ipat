# R9.64 — Commercial tenant Site/POP registry migration and acceptance

`0018_tenant_sites_staged.sql` implements a **separate first-class** `(tenant_id,code)` Site registry, site metadata versioning, append-only logical Site event records retained across Site deletion, a restricted nonlogin execution role and locked-search-path SQL functions with **current membership checks on each invocation**. They implement Site create, compare-and-set rename, guarded deletion and cursor-paginated lists (NOC only for an explicitly current POP grant). Device count comes from the server database, not another tenant's device list. The `managed_devices_registered_site_fk` is compound `(tenant_id,pop_id)` and is `NOT VALID` on historical rows when first installed; it immediately prevents **all new** unregistered or wrong-tenant assignments without guessing existing Site mapping. A candidate `tenant_site_bff.rs` transport-neutral Rust adapter requires a session+CSRF for writes and a server-derived verified Host tenant UUID, but remains **UNMOUNTED** until real OIDC/MFA + HTTPS + PostgreSQL shared session runtime are deployed. Neither the BFF nor SQL can send device commands.

## Controlled migration procedure — never execute against real VPS without approved owner recovery

1. Create a new independently recoverable backup and test it on an **isolated** PostgreSQL instance. Confirm actual tenant identity/membership, have tenant admins review their existing Site codes and take a transactionally consistent snapshot of all legacy managed devices. Hold read-only/maintenance gates for conflicting device registration during the migration window.
2. Only with approved production DB migration identity and rollback, apply `deploy/db/migrations/0018_tenant_sites_staged.sql` **once**, recording the schema release and exact SHA. It adds a NOT VALID composite FK: new writes are enforced immediately; previous `ipat_ops.managed_devices` rows are intentionally untouched and can be unresolved. No automatic `default`, string-to-Site matching, global Site import or cross-tenant copy.
3. Run **read-only** `deploy/db/migrations/0018_tenant_sites_backfill_preflight.sql` with the authorized migration owner. Independently verify the actual company and location for every `(tenant_id,pop_id)` displayed. The existing private owner JSON site names are NOT automatically mapped into commercial tenant data. Each approved tenant admin uses the future authenticated, narrowly scoped `create_tenant_site` path. Identity and zone checks must be current, not based on client-supplied tenant headers.
4. Rerun the read-only preflight. It must return **zero rows**. Apply `0019_tenant_sites_validate_fk.sql`; migration fails atomically if any orphan remains and PostgreSQL must attest `convalidated=true`. Rerun the row-count/tenant-crossing tests against the migrated **staging** database before commercial release. A partially staged 0018 schema without 0019 is never a passed production Site implementation.
5. Enroll only a dedicated nonlogin-function EXECUTE PostgreSQL service role to the verified identity-bound BFF runtime, with audited secrets outside Git and narrow DB networking; keep the underlying Site tables and audit inaccessible from API logins, browser and ordinary `ipat_app_runtime`.
6. Apply a separately approved real IdP/MFA, PostgreSQL, public ingress and rollback release. Explicitly test active vs revoked/suspended members, NOC exact POP, foreign company Site reference, stale updates, site still referenced by a Device, many concurrent creates and hostile Host/CSRF cases. Do not allow public commercial Site operations until those *live* tests pass.

**Recovery/downgrade:** restore independently tested pre-migration backups if any stage is found corrupt; avoid blindly dropping 0018/0019, which could silently orphan legitimately newly created Sites or devices. Rollback the application to read-only during investigation; require a migration review of newly created records before any controlled schema reversal. The unit/disposable acceptance is not proof of production PITR or vendor device recovery.

## Reproducible tests and limits

- `deploy/db/tests/test_tenant_sites_integration.py`, explicitly gated by `IPAT_PG_EPHEMERAL_TEST=1`, `PGDATABASE=ipat_synthetic`, `PGHOST=127.0.0.1`, synthetic password marker and the ordered disposable CI migrations. The existing R9.57 and R9.58 test suites run before it so it can prove rejection of 0019 with preexisting device rows, followed by explicitly synthetic tenant-approved backfill and successful validation. Never configure real credentials in the test environment.
- The `control-api` Rust unit suite covers strict Site ID/name validation in `tenant_site_bff.rs`; the physical read-only connector continues independently. This is an unmounted, commercial-path source boundary, **not** a real public Session↔Host↔tenant authorization test.
- The current R9.63 VPS running state and public prerequisites are documented in `docs/R963_PRODUCTION_RELEASE_GATE.md` and the PRD-wide audit matrix `docs/PRD_AUDIT_MATRIX.md`. No production PostgreSQL migration, OLT write, external firewall change or DNS repointing is performed by R9.64.
