# R9.70 — Confidential OIDC login and coherent English tenant console

**Source milestone; NOT public production deployment.** This closes two exact source-level workflow gaps remaining after R9.68/R9.69: the commercial tenant API had no real confidential OIDC authorization-code exchange/session issuer, and a successful browser session would redirect to `/dashboard`, a page that did not exist. Neither improvement grants permission to deploy against actual customer domains before real HTTPS, a reviewed Keycloak configuration, independent provider-console recovery and restored real PostgreSQL state are verified.

## Exact executable service topology

- `control-api` process A: `IPAT_R969_COMMERCIAL_SERVICE=YES` and existing independently protected R9.69 production DB configuration; binds exclusively to `127.0.0.1:3003` and mounts the R9.68 restricted tenant Site/Device/domain JSON API, **plus** `GET /`, `GET /dashboard`, static same-origin JS/CSS, `GET /api/v1/capabilities`, `GET /api/v1/device-catalog`, and authenticated `POST /api/v1/logout`. No tenant cookies are issuer authority.
- `control-api` process B: **different runtime DB identity** `ipat_oidc_session_issuer_login`, with `IPAT_R970_OIDC_ISSUER_SERVICE=YES`, `IPAT_R970_SINGLE_INSTANCE_OIDC=YES`, `IPAT_TRUSTED_HTTPS_EDGE=YES`, and `IPAT_R970_VERIFIED_CONFIDENTIAL_IDP=YES`; binds exclusively to `127.0.0.1:3004`. Only `/auth/oidc/start`, `/auth/oidc/callback` and its static completion redirect script are mounted. The in-memory pending PKCE state is deliberately SINGLE-INSTANCE and capped at 64 pending proofs; crashes expire pending logins rather than authorizing an unpaired callback. Durable *issued* sessions are in PostgreSQL. Multi-instance/HA IdP state is still a separate P0 production requirement, not silently implied.
- Real future reviewed TLS edge: explicit active tenant Host/SNI routing, `GET /auth/oidc/*` only to 3004 and `/dashboard`, `/api/v1/*`, `/dashboard/assets/*` only to 3003. Never forward any public route to legacy owner-private `:3002` or trust arbitrary client-supplied `X-Forwarded-Host`/identity headers. The edge must independently reject unregistered hostnames. The single-host issuer configuration is insufficient to serve *all* tenants and custom domains in general availability; a tenant-host keyed durable pending-state store and reviewed per-tenant IdP configuration are still outstanding.

## Nonsecret issuer deployment contract — DO NOT enable on current VPS

Runtime service environment must be protected and independently approved, **not** edited via customer dashboard:

- `IPAT_R970_ISSUER` — *reviewed* HTTPS issuer, e.g. `https://id.example.invalid/realms/ipat`; exact `/protocol/openid-connect/auth` and `/protocol/openid-connect/token` paths are fixed to that issuer. No HTTP, credential-in-URL, fragments, redirects or untrusted dynamic endpoint discovery.
- `IPAT_R970_HOST` — one exact verified active tenant DNS name behind a browser-trusted HTTPS edge (bare IP/non-DNS host rejected).
- `IPAT_R970_CLIENT_ID` — registered confidential Keycloak client ID. The IdP client must allow **only** `https://<IPAT_R970_HOST>/auth/oidc/callback` as the redirect URI; require PKCE S256, current MFA proof with signed `amr=mfa` and max authentication age of 300 seconds. Confirm Keycloak mappers actually emit the signed `amr` claims expected by the pinned verifier, without loosening the verifier to suit a demo realm.
- `IPAT_R970_CLIENT_SECRET_FILE`, `IPAT_R970_PUBLIC_KEY_FILE` — separate approved absolute owner-private (0700 parent, 0600 regular file) paths. Public key file is exact approved RSA PEM corresponding to a manually reviewed `IPAT_R970_KID` and issuer; confidential secret remains outside the repository, flags, command arguments and logs. Renew pinned keys through an independently reviewed rollout; do not auto-trust arbitrary JWKS URL headers.
- `IPAT_R970_DB_SOCKET`, `IPAT_R970_DB_NAME`, `IPAT_R970_DB_USER=ipat_oidc_session_issuer_login` — isolated issuer-only PostgreSQL Unix-socket identity. It can issue a session for a **separately verified signed browser identity and active same-tenant domain**, never read protected user/device tables, authenticate arbitrary sessions or perform tenant CRUD.

Only after independent security review should SRE create the actual nonroot service and narrow ingress routes; no root, firewall or DNS operation is executed by this milestone. Trusted HTTPS flags are declarations by the approved deployment system, **not proof** the edge is genuinely safe.

## Browser workflow and security details

1. A real active tenant operator opens the tenant host `/` and explicitly starts `/auth/oidc/start`. The issuer requires the exact configured Host and generates OS-random independent 256-bit state/nonce/PKCE verifier; stores only an ephemeral one-time proof locally. Browser receives a short-lived `__Host-ipat_oidc_state` cookie (`Secure; HttpOnly; SameSite=Lax; Path=/`) because a top-level GET callback after the cross-site IdP is expected.
2. Browser authenticates at the **fixed** reviewed Keycloak realm. The callback requires exactly matching Host/state cookie/query and consumes pending state **before** network or database calls. The issuer sends code, server-only PKCE verifier, callback URI and confidential secret to a fixed HTTPS token endpoint via bounded `curl` stdin, not argv/environment/logs. System TLS verification stays on; no proxy and no redirect are allowed. No token/cookie/secret appears in HTTP errors.
3. Existing `PinnedIssuer::verify_offline_browser_pair()` checks pinned RS256 ID/access signatures, nonce, matching identities, signed `amr=mfa` and independently short `auth_time`, audience, access token hash and token expiry. Only then `durable_tenant_session::issue_after_verified_identity()` resolves the exact **currently active** hostname/tenant/domain and current database membership, stores SHA-256-only cookie/CSRF digests and returns `__Host-ipat_session` (`Secure; HttpOnly; SameSite=Strict`) plus a separate non-HttpOnly CSRF cookie. Issuer process cannot call Site/Device/domain CRUD.
4. Callback displays a same-origin completion page and navigates to `/dashboard` from that page. This avoids browsers withholding a newly-set `SameSite=Strict` cookie during an immediate cross-site OIDC 303 chain. A manual accessible link is present without JavaScript. No client-side persisted token or credential exists.
5. `/dashboard` checks the database-backed active Host-bound session before rendering. JS then fetches `GET /api/v1/capabilities` from a narrow current-membership `SECURITY DEFINER` PostgreSQL function: by default **all navigation items are hidden**. A currently active `tenant_admin` sees independent Sites & POPs, metadata-only Devices, and customer-domain requests; unknown/revoked/suspended/foreign-tenant sessions cannot see those modules. The API independently repeats all current membership, POP and session/CSRF checks. NOC-specific navigation and complete role/locale parity are **not** claimed by this initial tenant-admin console.
6. Site create/list/rename/guarded-remove, catalog-backed Device Add/View/Edit/guarded Archive, domain request/list/disable and explicit CSRF-validated session revocation operate against the existing R9.68 API. Catalog names are inventory candidates, **not** physical vendor/firmware qualifications. All imported strings render via DOM text nodes, never `innerHTML`; local client menu state is never treated as backend permission. Physical OLT/ONT/RouterOS commands are absent from this general inventory console.

### Browser race discovered and fixed during synthetic acceptance

The first real local Google Chrome run (mocked synthetic API, *not* actual IdP or production PostgreSQL) PASSED independent Site registration but FAILED at metadata Device save. The Add Device Site selector became empty during an overlapping asynchronous reload of the same registered Site list; native browser required-field validation silently blocked the submit. Fixed `web/console/tenant/app.js` to retain the current selected Site across list fetches and explicitly preselect the Site newly created on the standalone page, then added contract regression checks for the preservation logic. On the rerun, actual Chrome passed four checked flows: standalone Site creation, Site-first catalog-filtered ZTE Saved/Not Connected record, domain Pending with synthetic TXT evidence and absolutely hidden tenant-admin menus for a simulated non-admin. The browser test intercepts **every** HTTP request to a reserved `.invalid` host and never contacts the owner VPS, any real IdP, DNS, customer, OLT or database. Its opt-in source is `deploy/scripts/lab/r970/owner_mac_synthetic_chrome_acceptance.cjs`; CI lints the script but does not require a provider Chrome installation.
