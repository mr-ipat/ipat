## Problem and product behavior

Owner screenshot: entering an SSH password and selecting Connect & Save looked like it had no effect because temporary lab owner verification was collapsed and not supplied. A previously implemented R9.48 fixed-target server draft was actually SAVED, but Device List was buried inside optional legacy diagnostics and the form did not separate save from authenticated connection. This created a misleading UX even while real VPS TCP route succeeded.

R9.49 delivers a **visible actual saved-device list directly underneath Add Device**, backed ONLY by the owner-private real `GET /lab/c320-owner-connection` source, never by synthetic demonstration devices. The form's SSH password is optional for **saving** nonsecret device metadata; Save Device & Connect persists the pending fixed C320 draft first, then automatically diagnoses the management network and begins the authenticated read when both device password and temporary lab owner code are present. The top-level status is split into **Saved Device**, **Connection Stage** and **Network / SSH Diagnostic**, so TCP success is never confused with successful SSH login.

If password is missing, display Pending SSH Password and retain the saved row. If owner code is missing, expand Advanced Security, focus the exact input and explain the short-lived LAB control; when the operator pastes or completes the one-time code, the currently pending save/connect attempt automatically resumes without another button click. If route or port fails, show documented stage codes and plausible causes without guessing a bad password from a timeout. If SSH challenge, auth/prompt or CLI parsing fails, return the previously whitelisted diagnostic class and leave the saved row Pending. Only an authenticated bounded physical card read may mark Connected read-only. On an API outage, keep a previously loaded saved row visibly present in the current browser session but change its status to UNKNOWN, never falsely green. Avoid storing credentials/code in browser local/session storage.

Real current owner-VPS observation at rollout: fixed owner-supplied C320 SSH management TCP reachable; owner-private draft `draft_saved=true` for DEV-01; `credentials_enrolled=false` and `device_status=PENDING`. This release did **not** receive an owner credential or exercise an actual new SSH authenticated login. Temporary owner code remains intentionally required because the private lab preview does NOT implement genuine authenticated production tenant-admin sessions. Source and stored code are already outside GitHub; neither a GUI-only bypass nor a hidden backend automatic privilege grant is acceptable. Generic vendor/per-tenant device enrollment and site-to-site tunnel automation remain unimplemented; don't advertise them as working.
